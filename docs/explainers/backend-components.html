The backend, component by component

A walk through backend/ as of 25 July 2026 — 48 Python files, about 12,300 lines across five packages. Read from the source, not from the docs.

The engine decides. Everything here exists to get a real household’s data in front of that decision safely, to move the money the decision names, and to prove afterwards that the decision was right — without ever becoming a second implementation of the engine.

01The shape

Three flows, one floor. Data comes in through the Plaid chain, goes out through the read paths, and money moves through the transfer saga. All three sit on the same scoped-Postgres floor, and every one of them crosses an authorization boundary before it touches a row.

The whole of it fits in one paragraph, and the rest of this page is detail underneath it. A request arrives carrying a Stytch session. identity/deps.py verifies the token against a cached signing key — no round-trip to the vendor — checks that the caller actually belongs to the household named in the URL, and hands the route a Repository that is bound to that one household and cannot be repointed. The route asks one of three assembly paths for a Snapshot, hands it to engine.decide(), and serializes what comes back. Separately and asynchronously, Plaid rings a doorbell whenever a bank has new data; that handler verifies the signature, writes the raw payload down, and enqueues — it never syncs inline, because a slow handler causes the retries that cause duplicates. And when a decision says to move money, a saga takes a lock on the (household, date, leg) slot, appends its intent to a ledger before calling the vendor, and today calls a provider that deliberately does nothing.

Two questions are worth holding as you read the rest, because most of the surprising code answers one of them: how does this stay scoped to one household? and what happens when this is delivered twice?

02db/ — the floor everything stands on

Four modules, SQLAlchemy Core rather than the ORM, and every dollar column NUMERIC — the same refusal to let a cent near a float that money() enforces inside the process. Two other choices here shape everything above them:

  • household_id, not user_id. A user is a login; the household is the tenant. One household may eventually have two logins — and for this product that is not a footnote, because a spouse’s spending is precisely what breaks a forecast.
  • RLS on every household-scoped table, and FORCED. A policy the table owner is exempt from is decoration.

Two layers, each tested with the other removed

db/repository.py is the fence; RLS is the backstop. Either alone would probably hold — and “probably” is not the bar for a table holding a household’s complete financial life. tests/test_idor.py proves each one with the other disabled, on the reasoning that defense in depth only ever tested end-to-end is one layer wearing a disguise.

@dataclass(frozen=True)
class Repository:
    conn: Connection
    household_id: str

    def cards(self) -> list[dict[str, Any]]:
        return self._all(
            "SELECT * FROM cards WHERE household_id = :h ORDER BY id"

Scope is a constructor argument, never a method argument. A per-call household_id is a thing someone forgets exactly once. There is no way to hold a Repository and not know whose it is.

And it is frozen, so a repository handed to a function cannot be quietly repointed at another household mid-call.backend/db/repository.py:31

household_scope() — the trap, and the spelling that avoids it

with conn.begin():
    conn.execute(
        text("SELECT set_config(:var, :hid, true)"),
        {"var": RLS_VAR, "hid": household_id},
    )
    yield conn
Transaction-scoped, never connection-scoped. Neon pools connections. A plain SET app.household_id persists for the life of the connection, so the next checkout from the pool inherits it — an IDOR wearing a security feature’s clothes. A test suite that opens one connection and reuses it never catches the difference.

And set_config(..., true) rather than SET LOCAL, not as style. SET is a utility statement and cannot take a bind parameter, so the only way to write it is to interpolate a request-supplied value into SQL. set_config is an ordinary function that takes the value as a parameter.

The safe spelling and the correct spelling turn out to be the same one. The obvious spelling is neither.backend/db/session.py:255
The measurement that turned a guard into a startup check

assert_rls_binds() refuses to start the process if the connecting role bypasses RLS. That is not defensive programming — Neon’s default role fails it.

A SUPERUSER or BYPASSRLS role ignores every policy silently: household_scope() still sets the variable, pg_policies still lists the policies, and every query returns every household’s rows anyway. There is no symptom until someone reads someone else’s financial life.

Measured against the real thing on 2026-07-16: Neon provisions neondb_owner with rolbypassrls = true. Connected as that role and scoped to one household, a SELECT returned both. So the obvious deployment — paste the connection string Neon hands you into DATABASE_URL — collapses defense-in-depth to one layer and turns the IDOR suite into a proof of a property production does not have.

codec.py and db/snapshots.py — the frozen snapshot

Every decision stores the entire input it was made from, not references to it. That is what lets the service explain a sweep years later after Plaid has rewritten the underlying history, show a regulator exactly what was known at the time, and replay a new engine version across every historical day to ask whether it would have overdrafted anyone.

codec.py is the tax on that: the snapshot is stored as JSONB, JSON has no decimal type, and a Decimal handed to json.dumps comes back a float. So each value is tagged with its type on the way out and reconstructed on the way in. The NUMERIC columns need none of this — only the JSONB payload does.

03The three read paths

The same Artifact shape comes back from three different assembly routes, and which one runs depends on what kind of household you are. The client cannot tell the difference, which is the point.

ModuleServesSnapshot comes from
readpath.py a seeded demo household Frozen — the snapshots rows the seeder wrote. Two queries for a window, not ninety get() calls.
livepath.py a household with live policy + attestation Re-decided — assemble_snapshot driven with the current policy() and attested_for().
linkedpath.py a real Plaid-linked household Assembled from rows — plaid_transactions becomes a sim.History the engine can decide against.

livepath.py closes a gap that is easy to miss and embarrassing to ship: the write paths persisted a user’s guardrails and attestation and read them back, but nothing fed them into a live decide(). A user could lower their buffer floor, Repository.policy() would return the new value, and the app would keep showing a decision computed from the old one.

What makes the fix careful is what it didn’t touch. assemble_snapshot stays a pure function of its inputs; the live values are passed in, exactly as sweeps_in_flight already was. The one canonical walk() grew a single attested parameter defaulting to True, so the seeder, the replay driver and the artifact builder are all unchanged — the regression oracle keeps grading the engine that shipped.

linkedpath.py names its own approximations

A linked household today is a Plaid Sandbox one, and the payment rail is in shadow — so a first-cut approximation is a wrong number on a screen, never a wrong transfer. That is what makes shipping v1 honest, and the two approximations (the card ledger anchored at the current balance; the inferred spec covering only payroll, bills and cards) are documented where they live rather than in a plan nobody rereads.

04The Plaid chain — how rows get in

Five modules in a fixed order, and the ordering rule is the same one twice: verify, persist, enqueue — never work inline.

  1. plaid/link.py — POST /plaid/link/exchange. A public token becomes a stored Item pinned to your own household. There is no household_id on the wire to smuggle; the target is derived from the verified session’s membership. It refuses an is_demo household outright, so a real bank item can never attach to the public demo plane — the two planes cannot cross.
  2. plaid/webhook.py — the doorbell. The endpoint is public and carries no API key, because Plaid does not have one. Its authentication is the signature.
  3. plaid/tasks.py — hands the work to Cloud Tasks with an OIDC token on the push target, so only Cloud Tasks as the configured service account can invoke the worker route.
  4. plaid/sync.py — the cursored /transactions/sync loop. Resolves the household through a SECURITY DEFINER lookup, takes SELECT … FOR UPDATE on the item row before reading the cursor so the two triggers cannot race into a double-insert, and is atomic: a failure mid-loop rolls back, so the cursor never advances past uncommitted rows.
  5. plaid/accounts.py — the balances and card terms /transactions/sync cannot carry. Transactions record what a household did; this records what is true now. Degrades to balances-only when the liabilities product was not consented, rather than failing the refresh.
    expected = claims.get("request_body_sha256")
    actual = hashlib.sha256(body).hexdigest()
    if not expected or not hmac.compare_digest(str(expected), actual):
        raise WebhookVerificationError(
            "the request body hash does not match the signed claim"
        )
Why the body hash and not just the signature. A valid signature replayed against a different payload would otherwise pass. The JWT commits to request_body_sha256, and this recomputes it over the exact bytes received — then parses only after the hash matches, so the parser never sees unverified input.

The alg is pinned to ES256 too, refusing the classic alg-confusion downgrade. identity/stytch.py mirrors this file deliberately, with two differences: RS256, and a TTL on the key cache rather than never-evict — a webhook JWT is single-use, but a session key is verified repeatedly, so a rotated key must stop being trusted within a bounded window.backend/plaid/webhook.py:95

The last link in the chain is recurring.py, which does no I/O at all. The engine forecasts against a payroll cadence and a set of scheduled bills; a real household arrives as a flat list of dated, signed, labelled movements with none of that structure. This is the pure function that recovers it — group by merchant, find what recurs on a regular cadence with a stable amount, return typed streams. It decides nothing about money. It only describes what has been happening, which is what lets a backtest grade the same detector production runs.

05identity/ — the edge

Two modules and one boundary, and the boundary is drawn so that swapping identity providers touches one file.

  • stytch.py verifies a session token locally against Stytch’s JWKS and returns the vendor’s user id. It is the only file in the codebase that knows the word “Stytch”. No per-request round-trip — a token is trusted on signature and expiry alone, which is what makes the hot path a local computation.
  • deps.py turns that into current_user (verify, then JIT-provision) and authorize_household (membership check, then a scoped repository). It names no vendor.

Three details in deps.py are worth knowing:

  • A bad token is refused before any provisioning. stytch.verify does not touch the database, so an attacker cannot make the service write a row for an unverified identity.
  • 403 is deliberately indistinguishable from “no such household”. A valid session naming a household it does not belong to learns nothing about whether that household exists.
  • Writes require owner. The role is read from household_members inside the scope, where RLS makes exactly the caller’s row visible.
The hole a role check could not see

authorize_household_owner is the write gate everywhere a household_id is in the path. But POST /households creates the very household a role would be scoped to, and POST /plaid/link/* is keyed to the user rather than a household — neither has a role to check.

Without a second gate, the public demo viewer could create a real household, become its owner, and re-open every write it had just been refused. That was measured as a 201 in production on 2026-07-21, not reasoned about. current_real_user is the fix, and it reads users.is_demo so a demo identity added later is refused with no code change — structural rather than configured.

06transfer/ — the write half

Paying a card is two legs: a debit (an ACH pull from checking into a platform funding account) and a payoff (a biller-payoff API landing that money on the card). Both sit behind one port so either vendor swaps without the saga changing. The money transits an FBO account we hold because Method’s source must be a platform account — an end-user’s checking cannot be one.

  1. provider.py — the TransferProvider port. Its four methods are shaped by what research found the real vendors actually do. Notably authorize is our step, not a vendor round-trip: neither vendor has a true two-phase authorize/submit, so it is the pre-flight re-check plus deriving the idempotency key from the (household, decision_date) slot.
  2. shadow.py — the first shipped state. ShadowProvider implements the full port, logs what it would do, and calls no vendor. Proven to touch no network in a test running under a socket that refuses to connect. Move nothing first.
  3. saga.py — submit_leg and apply_status. Built on the repo’s already-proven Cloud Tasks + row-lock durability pattern rather than Temporal.
  4. plaid_transfer.py · method.py · increase.py — the adapters. Translation only: pure, unit-tested behind a fake client, because translation is the part vendors surprise you on.
  5. webhook.py · reconcile.py — status arrives by webhook, verified and freshness-checked before it touches the ledger. And webhooks alone are not sufficient: Increase exhausts retries after ~72h and Method disables a webhook after repeated failures, so a periodic poll walks every non-terminal transfer and advances it against the provider’s own truth.

Why a duplicate submit is guarded by a lock and not a constraint

if already:
    return None  # the slot already reached submitted

repo = Repository(conn=scoped, household_id=intent.household_id)
auth = provider.authorize(intent)

_append("authorized")
ref = provider.submit(auth)          # the point of no return
_append("submitted", ref=ref.provider_transfer_id)
A duplicate submit is an overdraft, so this is the highest-stakes path in the service. It is guarded by a Postgres advisory transaction lock on the (household, decision_date, leg) slot, plus the check above that the slot has not already reached submitted.

A lock, not a UNIQUE constraint — the ledger is append-only, so corrections are new rows and a uniqueness constraint on the slot is ruled out. The lock serializes two concurrent first-submits, which is the race a constraint would otherwise have caught.

apply_status uses an advisory lock for a related reason: the app role holds SELECT and INSERT only, so it cannot take FOR UPDATE on a row — and the lock needs no row to exist.backend/transfer/saga.py:60

07The measurement layer

Five modules whose entire job is to check the engine, and the constraint they share is the most important one in the folder: none of them may become a second implementation of the engine.

ModuleQuestion it answersHow it avoids re-implementing
precompute.py What did the engine decide, day by day, for the demo household? Build-time only. Byte-identical output across runs — a test asserts it.
replay.py Was each decision right, against what the household actually did? Calls engine.outcome.grade(), which had existed since July 13 and had never been called. It changes no decision; it observes.
calibrate.py What would a looser spend model cost, across a population? Grades many households at several dial settings. A setting is licensed only if its breach rate is no worse than today’s.
trace.py Why that number, gate by gate? Reuses the engine’s own helpers and mirrors only the order. No gate’s value is recomputed.
artifact.py Did a refactor silently change what the engine decides? Nothing serves it any more — it is the golden fixture, checked day for day against seeded decisions.
An audit trail that is a second implementation is worse than none

trace.py reconstructs the whole gate sequence without re-deciding. Two things hold it honest: it calls the engine’s own _blocking_reasons, conservative_low_balance, untouchable, _cadence_hold, apply_caps and claimable_interest_avoided; and the headline it reports is decide()’s own output verbatim, not a reconstruction.

A test pins the mirror across the whole demo window: for every day, the terminal gate the trace lands on must match the action decide() actually returned. Reorder the engine and forget this file, and that test fails — which is the only acceptable way for an audit trail to drift.

The sequencing here is worth reading as a discipline rather than a workflow. The spend-model fix loosens the forecast and buys bigger sweeps — the one direction a change must never move without evidence. So the order was fixed in advance: land the grader, land the replay driver, ship the new model with its dial set to reproduce today’s refusals, and loosen it only as far as the measured breach rate licenses. replay.py is the evidence; calibrate.py is what reads a decision off it.

08assistant.py — the guard, not the prompt

Claude narrates; the engine decides. The model cannot compute a sweep, price interest or form a reason — those already happened, deterministically. Its only job is to answer a follow-up question about decisions that already exist, by retrieving them through two structured tools and describing what it found.

Why a guard and not a good system prompt

A system prompt asking a model not to invent numbers is a request. The contract here is that the product cannot state a financial claim it can’t trace to a Decision — and a request is not a contract.

So every dollar figure, outcome and reason code in the model’s final text is checked against the tool results from this turn before the user sees a word of it. Anything that doesn’t verify replaces the whole response with “no record.” That makes the guard, not the prompt, the actual test surface — which is why the test file spends most of its length trying to sneak a false claim past it rather than checking the happy path.

verify() enforces four rules in order of how much they matter. The first is the one that catches a recombination — every number real, the attribution false:

  • A dollar figure in a sentence that names a date must belong to that date’s decision.
  • A figure in a sentence naming no date must at least appear somewhere in this turn’s tool results.
  • An outcome asserted about a date must match that decision’s Action.
  • A reason phrase used about a date must belong to that decision’s codes.

The hard part is that a guard strict enough to catch a lie also catches the truth. A first version rejected the engine’s own copy on 82 of 90 days, because a sweep explanation legitimately names two dates — the day we acted and the projected low it was reasoning about — and only the first may carry a claim. What separates the two turns out to be word order: narration reaches the date through its figure (“a low of $748.79 on the 5th”), while an attribution leads with the date (“On the 5th we swept $748.79”). Same words, different claim.

09The five rules that explain the rest

  1. Two independent layers, each tested with the other removed. The repository fence and RLS. Defense in depth that is only ever tested end-to-end is one layer wearing a disguise — and the startup check exists because the guarantee is only worth what the connecting role makes it worth, which is a deploy-time fact no CI test can see.
  2. Verify, persist, enqueue — never work inline. Both doorbells. A slow handler causes retries, which cause the duplicates you were trying to avoid. Verification always precedes parsing, and the queue always precedes the work.
  3. One file per vendor. stytch.py is the only file that knows the word Stytch; each transfer adapter is the only file that knows its vendor’s shape; plaid/client.py is built lazily so a service with no Plaid credentials still boots and serves everything else.
  4. Refuse to boot rather than serve wrong numbers. DATABASE_URL, the RLS role check, the credential-at-rest guards, the operator password. A service holding bad data should not serve wrong numbers one request at a time — and the operator console refuses to start without a password precisely so the gap is loud rather than silent.
  5. Never a second implementation of the engine. trace.py mirrors order, not values. seed.py drives the one canonical walk() rather than writing its own ledger loop — a defect that had already happened twice before anyone noticed. replay.py calls grade(). livepath.py passes live values in rather than reading them inside the pure assembler.
