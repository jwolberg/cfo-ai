# Decision Engine Frontend MVP

## Summary

Add a React Native front-end MVP to cfo-ai: a single pre-authenticated demo household's
personal dashboard, backed by a small FastAPI service that runs the existing `sim/` and
`engine/` Python code to generate a real (simulated) decision history, plus an LLM
"explain this decision" assistant that narrates and retrieves from that history without
touching the decision logic. Deploys to GCP per `architecture.md`'s existing intent.

---

## Problem Frame

This repo currently proves the decision logic (`engine/`, `sim/`) and the product/strategy
argument (`docs/prd.md`, `docs/strategy.md`, `docs/architecture.md`), but has no
interactive surface — nothing a person can open and see the product working. It exists as
an interview-prep artifact for a founding engineer role at Resfi.ai
(`private/interview-prep-resfi.md`, `private/tech-prep.md`), and the job req names a
specific stack — TypeScript, React, React Native, Python, LLMs, Agentic AI Systems, RAG,
Cloud (GCP/AWS/Azure) — most of which the repo doesn't yet demonstrate. Without a front
end, the strongest evidence of engineering judgment (the refusal logic, the calibration
argument, the audit-friendly snapshot design) is legible only to someone willing to read
Python and markdown. A working demo makes the same argument visible in under a minute.

---

## Actors

- A1. Demo customer (Resfi persona): a simulated household with stable low-variance income
  and $8-40k revolving card debt, viewing their own dashboard; pre-authenticated, does no
  setup. See `USERS.md`.
- A2. Interviewer / reviewer: the actual audience for this artifact; evaluates engineering
  judgment and stack breadth by using the demo, not by reading code first.
- A3. Explain assistant (LLM): narrates `Decision.reasons` and answers follow-up questions
  about the household's own decision history; never computes or alters a decision.
- A4. Decision engine service (FastAPI): runs `sim/` + `engine/` to produce the household's
  transaction history and daily decisions; serves them to the app.

---

## Key Flows

- F1. Open dashboard
  - **Trigger:** app launch (pre-authenticated, no login)
  - **Actors:** A1, A4
  - **Steps:** app requests the demo household's decision history from the backend; if
    the backend is slow or unreachable, the app shows a loading state with a bounded
    timeout, then a defined fallback message rather than blocking silently; on success,
    backend returns precomputed daily decisions (sweep or refuse) across a fixed
    historical window; app renders summary stats (interest avoided, current buffer,
    targeted debt) above the fold, followed by a scrollable feed (most recent first)
    below.
  - **Outcome:** customer sees what the engine did, and did not do, without being told to
    look for anything.
  - **Covered by:** R1, R2, R3, R7

- F2. Ask "why" about a decision
  - **Trigger:** customer taps a decision (sweep or refusal) on the dashboard
  - **Actors:** A1, A3, A4
  - **Steps:** app opens the explain assistant with that decision's reason codes as
    context; assistant answers in plain language; customer may ask a follow-up ("why not
    last Tuesday?"); assistant retrieves other decisions from the household's own history
    to answer, never invents a number.
  - **Outcome:** every sweep and every refusal is explainable in conversation, not just as
    a static string.
  - **Covered by:** R4, R5, R6, R8

## Requirements

**Dashboard**
- R1. The app shows a single pre-authenticated demo household's dashboard on launch, with
  no sign-up, login, or account-linking step.
- R2. The dashboard lists the household's recent decisions (sweep or refuse) in reverse
  chronological order, each showing the outcome and its reason code(s) in plain language.
- R3. The dashboard shows summary stats computed from the same decision history: cumulative
  interest avoided, current available buffer, and the debt currently targeted (highest
  APR).

**Decision data**
- R7. All decisions and the underlying household history are generated by running the
  existing `sim/` household generator and `engine/decide.py` (and related engine modules)
  against a fixed seed — not hand-authored fixtures — so the demo reflects the actual
  decision logic.
- R9. No requirement in this set implies real Plaid connectivity or real money movement;
  every displayed decision is a shadow-mode "would have swept" record per `prd.md` §8.
- R13. If the backend is slow or unreachable when the dashboard loads, the app shows a
  loading indicator with a bounded timeout, then a defined fallback message — it never
  blocks silently or crashes.

**Explain assistant**
- R4. Each decision on the dashboard is tappable into an "explain this" assistant that
  narrates that decision's reason codes in plain language.
- R5. The assistant can answer at least one class of follow-up question by retrieving
  other decisions from the same household's history (e.g., "why not last Tuesday?"),
  demonstrating retrieval over the decision log rather than a single canned prompt.
- R6. The assistant never produces a financial claim (an amount, a sweep, a refusal) on
  its own — it only narrates and retrieves from `Decision` objects the engine already
  produced, matching `architecture.md` §3.5's existing principle.
- R8. If the assistant cannot answer from the household's own decision history (no
  matching record), it says so rather than inventing a plausible-sounding number.

**Platform and deployment**
- R10. The client is built in React Native (TypeScript), runnable during a live demo
  (simulator, device, or Expo web preview).
- R11. The backend is a small Python service (FastAPI, consistent with
  `architecture.md`) that serves the precomputed decision history and hosts the explain
  assistant's retrieval + narration calls.
- R12. The backend is deployed to GCP (Cloud Run, consistent with `architecture.md`'s
  existing intent), producing a URL usable in a live interview.
- R14. The deployed backend enforces a lightweight access control (e.g., a static API
  key or IP allowlist checked by the FastAPI service), distinct from the in-app
  no-login decision, so the public Cloud Run URL is not open to arbitrary internet
  traffic.

## Acceptance Examples

- AE1. **Covers R1.** Given the app is freshly installed, when it's launched, then the
  dashboard appears immediately with no login/signup/account-linking screen shown.
- AE2. **Covers R2, R7.** Given the demo household's precomputed decision history includes
  at least one refusal, when the dashboard loads, then that refusal appears in the feed
  with a human-readable reason (e.g., "connection unhealthy," not
  `CONNECTION_UNHEALTHY`).
- AE3. **Covers R5, R8.** Given the customer asks the assistant about a date with no
  decision in the household's history, when the assistant responds, then it states it has
  no record for that date rather than fabricating a decision.
- AE4. **Covers R6.** Given any assistant response, when reviewed, then it contains no
  dollar amount, sweep, or refusal that doesn't trace back to a `Decision` object already
  computed by `engine/decide.py`.
- AE5. **Covers R13.** Given the backend is unreachable, when the dashboard attempts to
  load, then a fallback message appears after a bounded timeout rather than an
  indefinite blank or loading screen.

## Success Criteria

- A person with no context can open the app and, within about a minute, understand what
  the product does (moves surplus cash to debt) and why it sometimes does nothing (the
  refusal gates) — without reading code or docs first.
- The demo visibly exercises TypeScript, React Native, Python, an LLM-backed assistant
  with retrieval (RAG) over real generated data, and a live GCP deployment — the job-req
  stack items this repo didn't previously demonstrate.
- `ce-plan` can pick this up without inventing dashboard content, assistant scope, persona
  details, or what's explicitly out of scope — this doc's Actors, Flows, Requirements, and
  Scope Boundaries already settle those.

---

## Scope Boundaries

- Real Plaid account linking or any real bank connection.
- Real ACH transfers or any real money movement — this MVP only ever displays what the
  engine decided in shadow mode.
- The overdraft-reimbursement guarantee (`prd.md` §2.3) — not applicable without real
  money movement.
- Onboarding, sign-up, login, or multi-user accounts — single pre-authenticated demo
  persona only.
- A live "run today's decision" action or real daily scheduler — decisions are precomputed
  across a fixed historical window at build/deploy time.
- Support for multiple households or user-editable policies (buffer, caps, blackout
  windows) — the demo persona's parameters are fixed.

---

## Key Decisions

- Generate decision history from the real `sim/` + `engine/` code rather than
  hand-authored JSON: the whole point of this MVP is to prove the Python/backend/engine
  work is real, not just the UI.
- Scope the LLM feature as narration + retrieval (RAG) over the engine's own `Decision`
  output, never as a second decision-maker: preserves `architecture.md`'s "LLM never in
  the decision path" principle, which is one of the repo's strongest arguments, while
  still covering the job req's LLM/Agentic AI/RAG line items.
- Single demo persona, pre-authenticated, no onboarding: removes the need for real
  auth/account-linking entirely, which isn't the point of this exercise.
- React Native as the one client codebase (with Expo web preview available for a
  browser-based demo if convenient) rather than a separate Next.js build: matches the
  user's explicit instruction and avoids maintaining two frontends for one demo.

## Dependencies / Assumptions

- Assumes `engine/` and `sim/` can run as-is inside a FastAPI service without
  modification (verified: both are pure-Python, no I/O, per `docs/decision-engine.md` and
  `README.md`).
- Assumes GCP Cloud Run plus a persistence layer (exact choice deferred to planning) can
  host both the precomputed decision history and the explain assistant's retrieval calls
  within the existing `architecture.md` shape.
- Assumes access to an LLM API (provider unspecified) for the explain assistant.

  The Problem Frame names "Agentic AI Systems" as a job-req stack item this MVP exists to demonstrate. Agentic AI denotes autonomous action — the opposite of what R6 and this design require. Resolve by either dropping the "Agentic AI" claim from the Problem Frame/Key Decisions (naming it an acknowledged gap) or explicitly reconciling how bounded narration+retrieval qualifies.
